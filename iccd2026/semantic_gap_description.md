在这里提到的 **“Semantic Gap”（语义鸿沟）** 是这篇论文最核心的立论支点。它指的是 **“大语言模型（LLM）的概率性、模糊性”** 与 **“形式化验证引擎的确定性、严谨性”** 之间不可调和的根本矛盾。

在你的论文语境下，这个“语义鸿沟”具体表现为以下三个维度的剧烈冲突：

### 1. 认知机制的鸿沟：概率生成 vs. 绝对决定论

* **LLM 的视角：** 它是基于概率分布的文本接龙模型。它理解的是“人类逻辑”和“高维意图”（例如：要触发这个 Bug，大概率需要先复位，再使能，再等待计数器溢出）。它给出的是一个**模糊的宏观方向**。
* **形式化引擎（Z3/SE）的视角：** 它是严密的数学机器。它理解的是“布尔可满足性”和“严格的 AST（抽象语法树）节点”。它要求的是**绝对精确的布尔逻辑约束**。
* **冲突结果：** 把 LLM 的“大概率建议”直接当作形式化引擎的“绝对数学约束”强行缝合，就像让一个写诗的文科生去直接指挥一台精密数控机床，必然导致系统崩溃。

### 2. 逻辑空间的鸿沟：LLM 幻觉 vs. SMT 死锁 (UNSAT)

LLM 无法保证输出 100% 契合底层的物理硬件实现，它的“幻觉”会在数学空间引发灾难：

* **词法幻觉（Syntactic Hallucinations）：** LLM 可能会捏造一个源代码里根本不存在的信号名（比如把 `enable` 错写成 `en`）。传统的符号执行引擎在解析时会直接抛出未定义变量异常，导致验证流水线**当场崩溃**。
* **物理悖论（Semantic Hallucinations）：** LLM 可能会给出一个在人类看来合理，但在硬件电路中物理上绝对不可能同时发生的状态组合。当引擎把这个里程碑喂给 Z3 求解器时，Z3 会立刻返回 **`UNSAT`（不可满足）**。如果引擎死板地坚守这个里程碑，它的搜索树就会在这里被完全剪断，导致陷入**永久死锁（Deadlock）**，从而产生严重的漏报。

### 3. 时间粒度的鸿沟：宏观步骤 vs. 周期级并发 (Temporal Mismatch)

* **LLM 的时间观：** 它是按“宏观步骤（Macro-steps）”来规划的，比如步骤 A 是“进入 Decode 状态”，步骤 B 是“计数器等于 1”。
* **硬件的时间观：** 它是基于时钟周期（Clock Cycles）和非阻塞赋值（NBAs）的。
* **冲突结果（时序跳帧/跳跃）：** 在真实的硬件运行中，由于并发逻辑的存在，状态机可能在一个时钟周期内直接从状态 A 跳到了状态 C，或者计数器一个周期加了 2（直接从 0 变到了 2）。此时，LLM 指定的那个里程碑（如 `counter == 1`）在物理时间轴上被跳过（Skipped）了。如果引擎没有容错机制，它就会在一个永远不会到来的状态前无限等待，浪费掉所有的算力和内存。

**总结来说：**
在 Introduction 中强调这个 **Semantic Gap**，是为了向审稿人证明：**“把 LLM 和符号执行结合，绝不是简单地写个 Prompt 调个 API 就能搞定的。”**

因为这个鸿沟的存在，**“朴素的融合（Naive Injection）”注定失败**。这自然而然且极其强烈地引出了你们的核心工作——设计 **MileSE 这样一套带有滑动窗口（Sliding-window）和架构解耦（Decoupling）的系统级容错框架**，来跨越这道鸿沟。
